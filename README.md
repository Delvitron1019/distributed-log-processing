# Distributed Log Processing

A PySpark pipeline that ingests raw event logs, aggregates them in parallel,
and writes analytics tables — benchmarked against a single-threaded pandas
implementation computing identical outputs.

**Everything here is reproducible from a clean clone.** No proprietary data:
the log corpus is synthetic and generated by a script in this repo, so the
benchmark numbers below can be re-run and checked.

---

## Results

Both engines computing identical outputs, same machine, same OS (WSL2 Ubuntu,
16 logical cores, 7 GB RAM), OpenJDK 17, PySpark 4.2.0.

| Rows | pandas (1 thread) | Best Spark | Winner |
|---:|---:|---:|:--|
| 1,000,000 | **19.8s** · 50.3k rows/s · 608 MB peak | 24.5s (`local[4]`) | pandas, by 1.24× |
| 4,000,000 | 61.5s · 64.8k rows/s · 1,959 MB peak | **35.8s** (`local[16]`) · 111k rows/s | Spark, by 1.72× |

**The crossover sits between 1M and 4M rows.** Below it, Spark loses at *every*
core count — the JVM, the query planner, and task scheduling cost more than the
parallelism returns. Above it, Spark pulls ahead and keeps going, while pandas'
memory grows linearly (608 MB → 1,959 MB for 4× the data) toward a hard ceiling
that Spark doesn't have.

### Core scaling changes shape with data size

| Cores | 1M rows | 4M rows |
|---:|---:|---:|
| 1 | 37.6s | 83.6s · 0.74× |
| 2 | 26.9s | 55.8s · 1.10× |
| 4 | **24.5s** | 41.0s · 1.50× |
| 8 | 25.3s | 36.8s · 1.67× |
| 16 | 27.1s | **35.8s · 1.72×** |

At 1M rows throughput **peaks at 4 cores and then declines** — past that point
each task is too small to justify its own scheduling overhead. At 4M rows all 16
cores still help, with diminishing returns (4→8 buys 12%, 8→16 buys 3%).

**How many cores are useful is a function of data size, not a property of the
job.** Sizing a cluster from a benchmark run on a smaller sample would
systematically under-provision. That is the finding this project exists to
support, and it is the opposite of what a single-scale benchmark would have
suggested.

Dataset: synthetic, 8 shards, 0.40% deliberately malformed lines
(227 MB at 1M, 907 MB at 4M).

### Row accounting

Every line is accounted for, which took a bug fix to achieve:

| | 1M corpus | 4M corpus |
|---|---:|---:|
| Physical lines | 1,000,000 | 4,000,000 |
| Parsed | 995,976 | 3,983,939 |
| Rejected (corrupt record) | 3,030 | 12,131 |
| Skipped by reader (blank lines) | 994 | 3,930 |
| **Unaccounted** | **0** | **0** |

The pandas and Spark readers originally disagreed on the reject count — 4,024
against 3,030 on the same file — while agreeing exactly on parsed rows. Spark's
JSON reader silently skips blank lines: it never emits a record for them, so
they are invisible even to the corrupt-record path. The pipeline now counts
physical lines separately with `spark.read.text()` and reconciles
`physical = parsed + rejected + skipped`, so a discrepancy would surface as a
non-zero `unaccounted` rather than as a quietly wrong denominator in every
error-rate metric downstream.

## The problem

Log analytics defaults to batch: collect all day, aggregate overnight, read
yesterday's numbers this morning. That's fine until you need to notice
something *while it is still happening* — an error-rate spike, a traffic
anomaly, a service degrading.

The engineering question is where the bottleneck actually sits. Naive log
processing is I/O-bound on parsing and shuffle-bound on aggregation, and those
two want opposite things from your partitioning strategy.

## What it computes

| Table | What it answers | Why it's here |
|---|---|---|
| `endpoint_stats` | Volume, error rate, p50/p95/p99 latency per endpoint | Wide shuffle over skewed keys |
| `error_timeline` | Error rate per service per 1-minute window | Surfaces incident windows |
| `service_health` | Per-service, per-region rollup | Cheap; small output |
| `top_users` | Busiest 1,000 users | ~120k distinct keys — the expensive one |

## Design notes

**Explicit schema, never inferred.** Schema inference costs an extra full pass
over the data, and it silently changes column types when a new file arrives
with a null column — the classic way a working pipeline breaks overnight.

**Malformed rows are quarantined, not dropped.** The reader runs in
`PERMISSIVE` mode with a corrupt-record column, so bad lines are counted and
separated. Knowing your reject rate is the difference between a pipeline you
can trust and one you hope about. The generator writes 0.4% broken lines
specifically so this path is exercised.

**Approximate percentiles.** `percentile_approx` is a single pass with bounded
error; an exact percentile needs a full sort within each group. On skewed
traffic that is the difference between seconds and minutes.

**The synthetic data is skewed on purpose.** Endpoint popularity follows a Zipf
distribution and latency is log-normal with a long tail. Uniform random data
would hide partition skew — which is the actual engineering problem worth
solving here — and would make p95 and the mean agree, which they never do in
reality.

## Running it

Requires Python 3.10+ and a JVM (OpenJDK 17).

```bash
pip install -r requirements.txt
```

Generate the corpus:

```bash
python generate_logs.py --count 1000000 --out data/raw
```

Run the Spark pipeline:

```bash
python src/pipeline.py --input data/raw --output data/agg --cores "*"
```

Run the single-threaded baseline:

```bash
python src/baseline.py --input data/raw --output data/agg_baseline
```

Reproduce the whole benchmark table:

```bash
python src/benchmark.py --cores 1 2 4 8 16
```

### On Windows

Spark needs Hadoop's native `winutils.exe` on Windows, which isn't bundled and
has to be sourced from a third party. The simpler route is WSL:

```bash
wsl -d Ubuntu
sudo apt-get install -y openjdk-17-jre-headless python3-pip
```

Then run the commands above from inside WSL.

## Limitations

- **Local mode, not a real cluster.** One JVM heap, no network shuffle. That
  cuts both ways: it understates shuffle cost and overstates how cheap
  coordination is. Numbers from a real cluster would differ, and I have not
  measured one.
- **The comparison is deliberately lopsided.** pandas was never designed for
  this, so "Spark beats pandas" is not a surprising claim. The question worth
  asking is *where* the crossover sits, which is why the table has two row
  counts rather than one.
- **An early version of this benchmark was invalid** — the pandas baseline ran
  on Windows while Spark ran under WSL, which is two operating systems and two
  filesystems rather than one experiment. The same workload took 29.2s on
  Windows and 19.8s in WSL, a 47% gap that had nothing to do with the engine.
  Both sides now run in the same environment.
- Batch over files, not streaming. `error_timeline` uses event-time windows and
  would port to Structured Streaming, but late-arriving events and watermarking
  are not handled.
- Output is overwritten each run — no incremental or idempotent writes.
- Executor failure mid-run is untested; local mode makes it hard to exercise.
- Tested at 1M events. The next bottleneck is likely the `top_users` groupBy,
  whose key cardinality grows with the user base rather than with traffic.
